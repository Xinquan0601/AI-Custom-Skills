# ADR-0006：重复导出只披露，不改写统计口径

- 状态：已采纳（2026-11-05）
- 相关：ADR-0001（实质会话口径）、ADR-0005（语义层）、`docs/stats-schema.md`

## 背景

同一场对话常被多个客户端各导出一份：opencode 在本地和 Linux 机器上的导出会分别带
`opencode-local:`、`opencode-linux:` 前缀，而另一份导出用原始 session id。三份的用户发言
完全相同，assistant 侧内容不完全相同（有的把思考过程也落成消息），工具调用数也可能因
采集时机不同而不一致。

10 月数据里，165 个会话中有 38 个属于这种重复（其中 23 个是实质会话）。语义层按
「项目 + 用户发言序列」合并成 77 场，于是报告里同时出现 100 和 77 两个数，读者无法判断
哪个是真实工作量。

## 决策

- **统计层不去重**：`totals`、项目、Agent、工具、代码、节奏全部按导出原值统计，
  `duplicates` 只给出组数、条数与其中实质会话数，并写进 `warnings`。
- **语义层去重**：facets 按会话合并，覆盖率用 `unique_tasks`，`duplicates_merged` 记合并数。
- **报告必须同时披露两个口径**：语义层章节写明「另有 N 条任务来自重复导出，已合并」；
  页脚的数据说明列出重复条数。不允许只给一个数、让读者自己猜。

## 理由

1. **不破坏历史可比性。** 去重会让「实质会话 100」变成 77，此前所有周报、环比、结论都失去基准。
2. **重复本身是数据质量信号。** 它说明导出链路在多客户端场景下还会重复采集，应该在
   AgentTrail 侧修；报告里抹掉它，等于把上游问题藏起来。
3. **两个口径服务两个问题。** 「我干了多少活」看原始统计（重复导出仍是同一段时间的两次记录，
   但事件表按发生次数计）；「我把哪些事做完了」看语义层（同一场对话只算一次）。

## 影响

- `stats.duplicates` 成为契约字段；`check_stats` 不强制，但报告会原样展示 `warnings`。
- 语义层覆盖率与统计层会话数不一致时，以「去重后会话数」解释语义层，以「原始会话数」解释统计层。
- 若将来在导出端修掉重复，`duplicates.extra_sessions` 归零，两个口径自然收敛，报告无需改结构。
