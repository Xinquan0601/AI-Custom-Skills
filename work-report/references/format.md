# 文体规格

从 2026 年 10 月的周报和月报正文反推出来的写法。所有示例都是用户原稿。

## 一、骨架

```md
# 工作周报 | 2026.10.08 – 2026.10.12

## DV454

### Alpine 客户

- 完成Code3控制程序与跨平台适配：GUI 经 MCU 下发 3 路开关，CAN 通信参数设为 250Kbps、采样点 75%，功能宏统一迁移至 CODE3 并在 DV424 平台启用
- 完成代码精简：清理 CODE3 程序遗留的冗余宏控与缩进导致的编译错误，完成公共配置及状态 ABI 去宏控重构
```

- 一级标题：`# 工作周报 | 2026.10.08 – 2026.10.12`，日期用 en dash，两侧空格。
- 系列：`## DV454`，大写，写全大写的四个系列名。本周没有内容的系列不出现。
- 客户组：`### Alpine 客户`。不要写序号，渲染器也不再补编号。
- DV460 / DV436 默认不分组，条目直接挂在系列下。

### 排序

- 系列顺序固定：`DV460` → `DV454` → `DV456` → `DV436`。没有内容的系列整段省略，但不许换位。
- 客户组按首字母排：拉丁字母在前（`Alpine` < `GMT` < `jiuyitong` < `xieli`），中文在后按字序（`军车` < `通用板`）。
- 同一系列在**周报和月报里的组顺序必须一致**，否则翻旧报告时找不到。

`render.py --check` 会校验这两条，顺序不对会报 warn。

## 二、条目

一条 = 一个状态词 + 一个主题 + 冒号 + 实测证据。

```
完成 <主题>：<证据，逗号连缀>
```

### 状态词

只有三个：`完成` / `未完成` / `进行中`，必须在句首、紧贴主题。用户原稿里也有「主题：完成 细节」的写法，本技能统一改成句首，否则计数会漏。

- `未完成` 只用于**没有结论**的事，且必须带阻塞原因或下一步：
  `未完成SATA1 6Gbps BadCRC 根因定位，需硬件做信号完整性判定`
- `进行中` 用于已经动手、这周没收口的事：
  `进行中bug7 定位：拔单探头连带消失 4 个，怀疑为同帧 0x400 整组上报`

### 证据

冒号后面必须有可核对的细节，靠这些撑住一条记录：

| 类型 | 实例 |
|---|---|
| 速率 | `顺序读 276MB/s、写 180MB/s`、`读速率 250–270MB/s` |
| 链路 | `成功建链 5.0GT/s`、`降速至 Gen2 3.0Gbps` |
| 串口 | `9600 8N1`、`115200 8N1`、`250Kbps / 采样点 75%` |
| 时序 | `增加 30ms 延时与写入确认`、`固定在开机 17 秒后产生一次离线报告` |
| 数量 | `7 块盘稳定在 GEN2`、`26 个可编译模块`、`22 个进程` |
| 地址 | `AA55 + Modbus CRC`、`同帧 0x400`、`GPIO4_A2` |
| 索引 | `单色灯对应 16、17、18 三个报警音索引` |

一条 **60–120 字**，这是目标区间。渲染器只在两种情况下报警：低于 40 字（细节明显不足）或超过 120 字（可能装了两件事）。40–60 之间不报警，但算偏薄，能补就补。

密度是优点，不要为了短而砍细节；素材确实没有可写的参数时，宁可留着短条，也不要编数字。

**拆分判据不是字数，是「一条里装了几件事」。** 只有下面两种情况才拆：

- 一条里有两个互不相干的结论，例如「查表失败致告警丢弃」和「RS485 无独立供电，静置 1 分钟后失效」是两次独立定位
- 一条混了完成和未完成两种状态，例如「DTS 修复完成」+「网口 RX 仍为 0」

单件事的两个阶段（建链 + 压测、定位 + 修法、协议统一 + 验证）**不要拆**，拆开只会剩下两条半句话：

```
✗ - 完成EBV3板 PCIe SSD Gen2 建链验证：新建 Gen2 DTS，v3 板成功建链 5.0GT/s
  - 完成PCIe SSD 高负载压测：顺序读 429MB/s、顺序写 300MB/s，112GiB 混合压测无掉线、零 AER 报错
✓ - 完成EBV3板 PCIe SSD Gen2 链路验证与高负载压测：新建 Gen2 DTS 成功建链 5.0GT/s，
    顺序读 429MB/s、顺序写 300MB/s，112GiB 混合压测无掉线、零 AER 报错
```

反过来，一条里只有一句结论、没有任何参数，就是「几乎没写」：`完成AC601 CAN 接口验证，通讯正常` 需要补上波特率、报文、实测现象里的任意一项。

### 括号

用户习惯把判断和后续动作塞进括号，不要在括号外另起一句：

- `（推测仍是高速信号问题）`
- `（后续凯淋排查出是电源端缺焊电阻导致的网卡 RX 不通，飞线后已成功启动）`
- `（4071 版本可复现，当时最新为 4081 版本）`
- `（待下需求单）`

### 不要写

- 不写价值句：不写「提升了效率」「保障了交付」「为后续打下基础」。
- 不写流程句：不写「首先…然后…最后…」。
- 不嵌套子列表，不用分号分点，全部逗号连缀成一句。
- 条目结尾不加句号。
- 不写文件路径，不写裸提交号（`a1b2c3d`），要写就写「合入 panic 按键离线判定补丁」这种语义描述。

## 三、正误对照

反例（本技能第一版写的，用户判为「不像」）：

```
- 完成 DV454 通用版的乘客计数核验工作
- 完成 RS232 透传服务的开发与联调
- 完成 RFID 未知卡问题的修复
```

正例（用户原稿）：

```
- 完成DV454_GMT 乘客计数功能核验：确认 RS232 通道已强制开启 PROTOCOL，定位到接收端读取配置原值会阻断通信链路，默认配置选用 RADAR 而 APC 乘客计数需要 PROTOCOL
- 完成RS232 监控通信落地与代码解耦：协议帧格式锁定 AA55 + Modbus CRC，业务逻辑解耦至独立文件
- 完成RFID 未知卡处理修复：旧逻辑只要有司机成功登录，后续未授权卡报警也计入该司机名下，新逻辑在登录状态刷到未授权卡先退出已授权司机再报警，不沿用上次姓名而是转换为 UNKNOW
```

差别不在措辞，在于**有没有给出可以拿去复验的东西**。反例只有动作，正例有通道名、帧结构、宏名、旧逻辑与新逻辑的分界。

## 四、月报

骨架同周报，两点不同：

1. 条目在组内自动编号 `1.` `2.`（渲染器加，正文不写）；客户组不编号。
2. 文首自动生成汇总表（系列 / 完成 / 未完成 / 进行中），由各 `##` 下的条目统计得出，正文不写表。

月报是当周报的合集，同一条在月报里可以更完整，但不要出现周报里没有的新事实。
